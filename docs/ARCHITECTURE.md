# System architecture

ASTRIX is a local mission-design game: static solo/shared-screen play requires no server; optional trusted-LAN play uses a Bun authority on the main computer. Core owns mission rules and simulation; it is an educational reduced model, not flight-qualified software. [Missions](./MISSIONS.md), [Simulation](./SIMULATION.md), [Resources](./RESOURCES.md), [Technical models](./TECHNICAL_MODELS.md), [Science UX](./SCIENCE_UX.md) and [Multiplayer](./MULTIPLAYER.md) explain the respective boundaries. [Verification](./VERIFICATION.md) records observed checks.

## Packages and authority

- `packages/core/src/contracts.ts`, `catalog.ts`, `models.ts`, `design.ts`: typed identity, paid hardware, quotes, planning and launch checks. `physics.ts` supplies the shared two-body geometry. `journey.ts` provides journey evidence and gates.
- `packages/core/src/sim/`: versioned flight snapshots, command transport, environment, stepping, crew support, telemetry, history and terminal evidence. `score.ts` scores the frozen flown design.
- `packages/core/src/interop/`: inert GMAT initial-state import/export and sampled-trajectory parsing; viewer data is separate from a game flight and cannot establish resource or score state.
- `packages/data/`: local snapshots, source records, science topics and explicit context bindings. Core depends on data, not vice versa.
- `packages/session/`: pure shared authority over core: journey/artifacts, typed re-quoted edits, approval dependencies, stable player attribution, roster/trade/note records, command batches, pause/decision policy, attempts and practice checkpoints. `reduceSession` owns mission transactions; `tickSession` owns bounded clock progression. It imports no browser, storage, audio or transport implementation.
- `apps/host/`: Bun HTTP/WebSocket host, explicit LAN-interface selection, loopback-only bootstrap, admission/device tickets, serialized room queue and monotonic clock. It serves the built web app and holds the room in memory; it is not an internet service or durable flight database.
- `apps/web/`: `ui/shell` (identity top bar, Help), `ui/hud` (resources), `ui/guide` (bottom MissionControl, CAPCOM, Show me), `ui/tour`, `ui/layout` (panels, tracked placement), `ui/flight`, `ui/forecast`, `ui/inspector`, `ui/recovery`, `multiplayer/` (transport and reconnect) and `three/` (scenes, spacecraft, camera). The zustand mission store projects session state and dispatches intents; settings, sound, explanatory snapshots/focus, role-tab selection and camera remain device-local. `liveMission` is a read-only derived selector, not a second writable simulation. One persistent R3F Canvas renders model-derived scene data; visualization is not a second physics authority.

Static solo/hot-seat uses the pure authority directly, with browser scheduling and no server dependency. The remote projection boundary is `setIntentSink` / `applyRemoteSnapshot`; remote mode cannot step a local flight, including after disconnection. Transport authenticates devices and constructs actors before reduction; host capability permits administration but never bypasses a discipline's physical permissions. Stable player IDs are separate from roles and devices. The LAN runtime, host lobby and phone pairing/readiness/presence surface are implemented; dedicated phone design/flight consoles and physical-device qualification are not. See [Multiplayer](./MULTIPLAYER.md) for deployment and limits.

The versioned wire contract validates every client variant at runtime, rejects unknown fields and arbitrary design/simulation writes, and binds transactions to epoch, attempt, roster and design revision. Accepted/refused results are correlated by device/intent ID; exact duplicates retrieve the saved result, while changed payloads cannot reuse an ID. Public snapshots explicitly project bounded history, receipts, events and checkpoint summaries, excluding credentials, private quotes, result ledgers and replay records; full history is separately paged with attempt-bound cursors. Ordered intent actors and clock advances form the replay record against the exact rules/data build. Ledgers have finite room-lifetime limits and refuse overload before further mutations.

`LOCAL_RESTORE` is a trusted static renderer-preparation rollback, and `LOCAL_TRADE` preserves the static budget-comparison action. Neither has a wire form; the parser rejects both. Transportable comparison evidence uses `recordTradeQuote` / `RECORD_TRADE` so the authority reconstructs the quote instead of accepting client budgets. Browser preferences, previews, explanation focus, tours and camera actions are local-only, not mission-state patches.

Replay retains at most 20,000 transitions before rolling to an explicit private authority checkpoint plus suffix; replay starts from that recorded baseline rather than pretending earlier history remains. Results retain at most 10,000 device/intent outcomes per epoch, after which new mutations return `RATE_LIMITED`. Quotes expire after 120 authoritative commits, and immediately become unusable on the bound design/attempt/roster change; this is a transaction-count lifetime, not a wall-clock guarantee. LAN pending spacecraft commands are capped at 64, in addition to core's 128 completed receipts, so public queues preserve every pending command within a finite bound.

## Identity, workflow and transactions

Rules version 4 requires `Design.levelId` and `Telemetry.levelId`: `ASPIRING` or `EXPERT`. Attitude is a rate-limited body-to-MJ2000Eq quaternion (+X solar-panel normal, +Z instrument/antenna boresight), not a rigid-body torque model. Presentation depth (`GUIDED`/`DETAILED`) stays independent; its initial value follows level unless explicitly chosen. Aspiring offers spotlight tours, state-driven guidance and assisted checkpoints; Expert exposes detailed engineering and on-demand teaching. Neither level repairs hardware automatically. Score identity contains scenario, level, rules, seed and assistance; older incomparable bests remain separate.

The journey is `NEED_GOALS → CONCEPT → REQUIREMENTS → DESIGN → BUILD_VERIFY → IMPLEMENT → REVIEW`. Earlier stages are editable before launch; final Review requires a terminal flight. A brief and segment choices are player decisions, while modeled requirement checks and readiness are computed evidence. A real quote supplies before/after budgets for a trade. Freeze and verification are bound to a design revision; launch explicitly rechecks current readiness and signoffs. A stale proposal cannot overwrite a newer design. Viewing, explaining, acknowledging, or completing readiness does not launch or resume a flight.

The HUD presents five chapters over these seven gates. The bottom contextual MissionControl owns the sole primary Continue/action, chapter and substep navigation, Requirements/Slots/Checklist/Flight trays, and tool visibility buttons. Trays are mutually exclusive; navigation cannot bypass journey gates. CAPCOM resolves requirements, cues and blockers into a next action; Show me expands and highlights its existing control but never completes work. The header carries identity, not a competing Continue. Quotes, approvals, freeze and launch remain explicit core/session transactions.

The four concurrent disciplines are Science, Spacecraft, Launch/Orbit and Ground/Comms. Explicit solo mode uses actor `ALL`; team mode requires the selected owned discipline even if one player owns all roles. Static shared-screen players are local identities, not authenticated remote devices. Commands retain issuing stable player ID separately from current role ownership. Roster changes preserve already-issued actors and invalidate affected approvals; unrelated design changes preserve approval evidence where core's affected-role selector allows it. Design and flight state are immutable across public transactions; a refused command batch never commits its candidate state.

## Flight and rendering

`createSim(design, seed)` freezes an eligible design. `stepSim` integrates on a fixed grid and scheduled deadlines; `issueCommand` distinguishes acceptance, queued transport and execution. Ground requests need contact and may experience light time. Onboard procedures operate without radio but consume modeled time; confirmed `endMission` is an immediate session action. `telemetry`, `nextBoundary`, `history`, `historyInfo` and `attemptAudit` expose core quantities and qualified forecasts. A practice rewind restores a coherent prior snapshot and records assistance; it does not repair the current state.

The canonical orbit stores body, UTC epoch, MJ2000Eq frame, semi-major axis, eccentricity, inclination, RAAN, argument of periapsis and true anomaly. Altitude controls convert into that representation. Game time is relative to the explicit epoch. A sampled external trajectory is a separate visual product; imported initial conditions do not import a GMAT force model or operational plan.

The setup flow prepares the renderer before committing an attempt and retains rollback on cancellation. Once mounted, the simulator and Canvas remain available while Home, windows, explanations or optional tools are shown. A pause reason can be removed without implicitly resuming; camera movement, explanations and display changes never command the spacecraft. Resources and physics originate in core selectors, not React.

`forecastTimeline` samples shared environment geometry without mutating flight state. The read-only dry run calls `forecastMission` in a cancellable Web Worker, with ordinary transported commands and a disclosed deterministic policy. Results are local presentation, never a flown score. Timeline and dry-run horizons are bounded; forecasts are not guarantees.

Manual attitude targets are serializable `ATTITUDE_TARGET` commands: ground transport for uncrewed missions, onboard for crew. The UI throttles gestures; the session rejects manual inputs above 10× warp. Only unsent targets from the same actor/gesture coalesce; transmitted targets cannot be recalled. Renderers consume pose through `useMissionPose()`; camera/pilot mode, panel geometry, quotes, tours, highlights and component inspection remain device-local. The Component panel reads catalogue data and core telemetry only; on desktop a scene tracker writes the inspected part's projected screen bounds outside React state each frame, and the panel follows them until the player moves it.

The static bootstrap has its own styled loading/failure surface before React. Root and workspace error boundaries preserve diagnostics; workspace failure pauses flight without destroying the Canvas, and retry never resumes time. Unknown addresses show a localized 404 and add a blocking route pause. Returning Home retains the mounted attempt. A standalone `404.html` is also built for static-host error routing.

## Persistence and limitations

The active attempt, commands, history, checkpoints and role assignments are session state. Static browser reload is not a flight restore. In LAN mode a browser refresh can reconnect and rehydrate the room while its Bun process remains alive; stopping that process loses the in-memory room. Device reconnect credentials are not authority snapshots. Settings, per-tour completion (`astrix.tours.v2`) and rules-versioned best scores remain separate from flight state. Historical scientific snapshots are local; external source links require connectivity. No account, internet room, durable server recovery, real agency approval, development calendar, medical model, live data feed, or full GMAT dynamics are implied.
