# Space Mission Design Game: acceptance checklist

Reference: https://www.spaceappschallenge.org/2026/challenges/space-mission-design-game/ (rendered Details page read 2026-11-14 during implementation).

The challenge explicitly encourages simplified models and explanations accessible without advanced knowledge. Guided presentation therefore supports the objective; it must not remove the trade-offs.

| Official objective | ASTRIX acceptance scenario |
|---|---|
| Define an objective and mission requirements | Both levels choose a destination-compatible goal and bounded ambition, with actual target, allowance and deadline visible together |
| Configure spacecraft and instruments | Compare paid hardware kits and approach choices; inspect exact installed parts without mandatory subsystem forms |
| Interacting mass, power, budget, data and communications limits | Core budgets and real reference-policy certification; no viable badge from compatibility alone; preview and receipt preserve W/Wh, stored/returned data and finite inventories |
| Choose launch and orbit | Provided-orbit or powered surface-launch families, fuel-limited burns and Earth/Moon patched conics; analytical Mars capture remains separate |
| Manage a mission from concept to operation | Discovery → Design & Play → decision preview → explicit commit → consequence → debrief/retry, without stage/signoff ceremony |
| Strategic decisions | Bounded operational plans trade elapsed mission time, reserve and useful output; hazards interrupt rather than being skipped by a cinematic |
| Feedback and mission evaluation | Actual objective evidence, turn receipts, failure causes, qualified identity and discovery journal |
| Solo or collaboration up to four | Local play or one LAN host plus three admitted controllers; phones propose, the host commits, stale/double requests cannot execute twice |
| Different scientific knowledge levels | Same clear loop for Aspiring/Expert, optional details/hints and harder tradeoffs rather than an expert-only studio |
| Understand why a decision changes mission performance | Preview versus measured receipt, exact resource/evidence values, attributed references and explicit model limits |
| Repeat and learn | Same-condition retries, changed-design experiments and version-qualified comparisons; assisted checkpoint retry is labelled |
| Optional realistic interchange | Bounded OEM/ReportFile visualization and supported GMAT initial-state scripts; no arbitrary script execution or claim of reproducing GMAT dynamics |

The product is a bounded learning game, not unrestricted astrodynamics or flight qualification. General-purpose mission authoring is no longer the player-facing goal. Ascent and lunar flight remain reduced models; no landing or crew lunar return is implied. Crew support/recovery is abstracted, not individual physiology. Release evidence belongs in [Verification](./VERIFICATION.md).

## Evidence policy

Claim completion only after observing it. Automated physics, browser and desktop HTTP/WebSocket checks are not a human enjoyment study or physical-phone qualification. No internet matchmaking is implied. Authored assumptions, NASA measurements, calculated game values and heuristic USGS product matching must remain distinct.

NASA-resource eligibility and team registration are submission concerns, separate from gameplay acceptance. Do not claim organizer approval or GMAT validation without obtaining it.
